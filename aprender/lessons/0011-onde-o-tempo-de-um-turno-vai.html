Onde o tempo de um turno vai — medir antes de mexer

O relato foi "ficou mais lento depois do deploy". Essa frase sozinha não diz o que consertar — podia ser a máquina do Fly.io acordando do zero, podia ser uma query que cresce com o tamanho da sessão, podia ser só a Groq mesmo. Esta lição é sobre como separar essas hipóteses com números reais em vez de achismo, e sobre um efeito colateral que não tinha nada a ver com o código: o Windows bloqueando o próprio ambiente de desenvolvimento.

~10 minutos Arquivos: Backend/app/infra/tracing.py · Backend/app/infra/embeddings.py · Backend/app/routers/game.py Lição 10 — do localhost à internet ↗

Um turno não é uma coisa só — são quatro

"O turno demora" esconde que um turno de /chat/stream passa por pelo menos quatro fases com donos completamente diferentes: recuperar memória (uma query no banco + um embedding local), montar o contexto (RAG sobre a bíblia, também com embedding), o laço do agente (uma ou mais chamadas de verdade à Groq, ADR-0007) e escrever de volta (persistir o turno, atualizar o resumo rolante). O Langfuse (Etapa 9) já instrumenta a terceira — é uma trace por chamada real ao modelo. As outras três não apareciam em lugar nenhum.

Por que isso importa antes de otimizar qualquer coisaSem saber qual fase pesa, "otimizar" vira chute — trocar de biblioteca, cachear algo, reescrever uma query, tudo com a mesma confiança e metade tendo zero efeito no número que o jogador sente. A Etapa 6 já tinha essa regra para qualidade (não confiar em "parece melhor"); a Etapa 10 aplica a mesma regra para performance.

Instrumentar sem instalar nada novo

A medição usa só time.perf_counter() e um logger.info, dentro de um context manager pequeno:

# app/infra/tracing.py
@contextmanager
def medir(fase: str, **contexto: object) -> Iterator[None]:
    inicio = time.perf_counter()
    try:
        yield
    finally:
        duracao_ms = (time.perf_counter() - inicio) * 1000
        logger.info("latencia fase=%s duracao_ms=%.1f %s", fase, duracao_ms, contexto)

Diferença chave em relação ao Langfuse: medir() loga sempre — em produção e em dev, com ou sem conta configurada. Um `grep latencia` no log de produção já dá amostra suficiente para p50/p95 de verdade, sem precisar de outra ferramenta. Envolvendo a recuperação de memória e o laço do agente:

with medir("memoria", personagem_id=heroi.id, turno=w_state.turno):
    memorias = memory.memorias_relevantes(db, heroi.id, user_input.action, w_state.turno)
...
with turno_span(...), medir("agente", personagem_id=heroi.id, turno=w_state.turno):
    for evento in executar_turno_stream(msgs, executor):
        ...

Cinco turnos reais (não mockados) contra a Groq deram: memoria p50 58,8ms / p95 61ms — agente p50 2179ms / p95 5957ms. A diferença de ordem de grandeza já responde a primeira pergunta: o laço do agente domina o turno de longe. Isso não é uma ineficiência do projeto para corrigir — é o custo real de estar chamando um LLM, possivelmente mais de uma vez por turno (uma ferramenta chamada = uma chamada nova ao modelo, ADR-0007). Nenhuma correção de código muda essa ordem de grandeza; só troca de modelo ou menos chamadas por turno mudariam.

Duas famílias de lentidão pedem duas provas diferentes

O relato "ficou mais lento depois do deploy" apontava para uma família específica: o que só existe em produção, porque só lá a máquina desliga sozinha (min_machines_running = 0, fly.toml) e reboota no próximo pedido. Não dá para medir cold start em localhost — a máquina de dev nunca desliga. A prova aqui teve que ser outra: docker build e docker run reais, olhando os logs, não um número de p50/p95.

Onde moraComo provar sem produção

Custo por turno (Família 2)medir() com turnos reais, em qualquer ambiente — localhost serve

Pagar o custo antes, não durante

O modelo de embedding (fastembed, usado pela memória de longo prazo e pelo RAG da bíblia) carregava lazy — na primeira vez que qualquer coisa precisasse dele. Numa máquina que acabou de ligar, essa "primeira vez" é dentro do turno de um jogador de verdade, baixando o modelo do HuggingFace ao vivo. A correção é um padrão que vale para qualquer custo de inicialização caro: mover o carregamento para o boot, não para o primeiro uso — um lifespan do FastAPI que roda antes do servidor aceitar qualquer pedido:

# app/main.py
@asynccontextmanager
async def _lifespan(_app: FastAPI) -> AsyncIterator[None]:
    embeddings.carregar_modelo()
    yield

app = FastAPI(title="Mestre.IA", lifespan=_lifespan)

Sozinho, isso só move quando o download acontece (ainda no boot, ainda lento) — não some com ele. A segunda metade é baixar o modelo em build time, dentro do Dockerfile, para o boot só ler do disco:

# Dockerfile
RUN uv run --no-dev python -c \
  "from app.infra.embeddings import carregar_modelo; carregar_modelo()"

Com as duas peças juntas: build baixa uma vez por imagem (~15s, medido no docker build real), boot só carrega do cache (~1,1s, medido no log do docker run) — nenhum jogador paga o download, nunca.

Onde o cache mora importafastembed usa /tmp por padrão. Alguns runtimes de container montam um tmpfs próprio por cima de /tmp — o que apagaria um cache baixado em build time antes do container sequer subir. A correção: cache_dir explícito dentro de /app, uma pasta comum da imagem, sem essa armadilha.

Mover trabalho para depois da resposta não é mentira sobre o total

Duas peças da escrita final — atualizar o resumo rolante (pode chamar o modelo de novo) e registrar o evento de memória (calcula um embedding) — aconteciam antes do jogador ver a resposta. O trabalho total não muda ao mover isso para depois; o que muda é quem espera por ele. Em /chat (que devolve uma resposta só), isso é literalmente o BackgroundTasks do FastAPI:

db.commit()
background_tasks.add_task(_persistir_memoria_em_segundo_plano, heroi.id, ...)
return _resposta(...)

Em /chat/stream a solução é diferente, e o motivo é interessante: a rota é def, não async def — devolve o StreamingResponse antes do generator sequer rodar, então não existe BackgroundTasks injetável ali dentro. O Starlette resolve isso com background= no próprio Response, que roda **depois que todo o corpo já foi entregue ao cliente**:

resultado_pos_stream: dict = {}

def gerar():
    ...
    resultado_pos_stream.update(heroi_id=heroi.id, ...)
    yield _sse("state", ...)   # o jogador já recebeu tudo neste ponto

def _tarefa_pos_stream():
    if resultado_pos_stream:
        _persistir_memoria_em_segundo_plano(**resultado_pos_stream)

return StreamingResponse(gerar(), background=BackgroundTask(_tarefa_pos_stream))

O dicionário mutável (resultado_pos_stream) é a ponte entre os dois escopos — o generator só sabe os valores finais no fim de si mesmo, e a tarefa de fundo só existe fora dele. E a tarefa usa uma SessionLocal() própria, não a sessão do pedido: pelo tempo em que ela roda, o pedido original já pode ter terminado de vez.

O achado que não tinha nada a ver com o código

Verificar os dois primeiros pontos exigia docker build de verdade — e o Docker Desktop desta máquina não subia, com um erro de socket interno ("The file cannot be accessed by the system"). A causa raiz, achada lendo o log de erro do próprio Docker: o Acesso Controlado a Pastas do Windows Defender bloqueando o Docker de gerenciar arquivos em AppData\Local\Docker. Depois de liberar o Docker Desktop nessa lista, o Docker voltou — mas o python.exe do ambiente virtual, que não estava na lista, passou a ser bloqueado de criar pastas novas dentro do projeto (que vive em OneDrive\Documentos\..., também protegido por padrão). ruff, pytest e o próprio fastembed pararam de conseguir criar suas pastas de cache — todos com o mesmo sintoma, todos resolvidos rodando sem cache ou apontando para uma pasta fora da árvore protegida.

O mesmo padrão da Lição 10, de novoNenhum desses dois problemas (Docker, Acesso Controlado a Pastas) é bug de lógica — são a borda entre o código e o ambiente que o executa. pytest/ruff/mypy continuaram verdes o tempo inteiro; nada disso aparece rodando a suíte. Só apareceu tentando rodar a coisa de verdade contra um ambiente real — desta vez não era rede nem SDK, era o próprio sistema operacional decidindo, por segurança, que um processo não confiável não pode criar arquivo.
