Lição 05 · Mestre.IA

Anatomia de uma chamada com ferramentas — e por que a descrição é prompt engineering

Até a Etapa 3, o "juiz" já existia — rules_engine.py rolava o d20 de verdade. Mas o modelo ainda dizia o que queria fazer escrevendo {"comando_combate": {"tipo": "atacar", ...}} dentro do mesmo JSON da narrativa: um campo que o servidor confiava por convenção de nome, não por contrato. A Etapa 4 troca isso por tool calling nativo — o modelo chama atacar(alvo="Goblin", arma="Cimitarra") como uma função de verdade, validada pela própria API antes de chegar ao seu código. Esta lição abre essa caixa: o que exatamente vai no fio, por que isso não é mágica, e um achado desconfortável — ter a ferramenta certa não significa que o modelo vai usá-la.

~12 minutos Arquivos: app/services/tools.py · app/services/agent_loop.py · scripts/tool_call_accuracy.py Lição 4 — determinismo e semente ↗

O que "tools=[...]" realmente é: JSON Schema, não configuração

Quando services/agent_loop.py chama chamar_com_fallback(msgs, tools=TOOLS_SCHEMA, tool_choice="auto"), o parâmetro tools não é um objeto especial de nenhuma linguagem de IA misteriosa — é JSON Schema puro, o mesmo formato que valida a resposta de qualquer API REST. Cada ferramenta em app/services/tools.py tem essa forma:

{
  "type": "function",
  "function": {
    "name": "gastar_ouro",
    "description": "Debita ouro do herói — compra, suborno, pagamento de taxa. Falha se não houver saldo.",
    "parameters": {
      "type": "object",
      "properties": {"qtd": {"type": "integer", "description": "Quantidade de ouro a gastar."}},
      "required": ["qtd"]
    }
  }
}

Isso vai literalmente dentro do corpo da requisição HTTP para a Groq, junto com as mensagens. O modelo não "sabe" Python, não importa tools.py — ele lê essa descrição em texto, no mesmo contexto onde lê a bíblia do mestre e o histórico da conversa, e decide (é uma decisão probabilística, não uma chamada de função de verdade) se algum trecho da resposta dele deveria ser uma chamada a uma dessas funções. Quando decide que sim, a API devolve message.tool_calls — uma lista de {id, function: {name, arguments}}, onde arguments é uma string JSON, não um dicionário Python. A validação de schema (tipo certo, campos obrigatórios presentes) acontece do lado da Groq antes disso voltar pra você — é isso que elimina a classe de bug que existia até a Etapa 3: dados.get("comando_combate") or {} não tinha garantia nenhuma de forma.

Por que uma chamada não basta: o loop

app/services/agent_loop.py:executar_turno não faz uma chamada, faz até max_passos:

for _passo in range(max_passos):
    resp = chamar_com_fallback(msgs, tools=TOOLS_SCHEMA, tool_choice="auto")
    mensagem = resp.choices[0].message
    if not mensagem.tool_calls:
        return mensagem.content or "", executor.eventos, chamadas
    msgs.append({"role": "assistant", "tool_calls": [...], ...})
    for tc in mensagem.tool_calls:
        resultado, sucesso = executor.executar(tc.function.name, tc.function.arguments)
        msgs.append({"role": "tool", "tool_call_id": tc.id, "content": json.dumps(resultado)})

A razão é simples: uma resposta com tool_calls não tem narrativa nenhuma junto — o modelo "gastou" a resposta chamando a ferramenta, e precisa ver o resultado dela (a mensagem role="tool" que você anexa de volta) antes de conseguir escrever a prosa. É por isso que um turno de combate no Mestre.IA é, no mínimo, duas idas e voltas: uma para chamar atacar, outra para o modelo receber "ACERTO, 6 de dano, Goblin: 1/7 PV" de volta e então narrar a cena com esse resultado em mãos. max_passos (padrão 6, settings.agent_max_passos) existe porque nada impede, em teoria, um modelo entrar num ciclo chamando ferramenta atrás de ferramenta sem nunca "terminar" — um loop sem limite é uma cota da Groq sendo consumida em segundos, não minutos.

O tool_call_id não é decorativoCada chamada tem um id (tc.id), e a mensagem de resposta precisa referenciar esse mesmo id em tool_call_id. Quando o modelo pede duas ferramentas no mesmo passo (aconteceu ao vivo: rolar_teste + consultar_regra juntos), é assim que ele sabe qual resultado pertence a qual chamada — sem isso a conversa ficaria ambígua sobre "o resultado que acabei de ver era de qual das duas coisas que eu pedi?".

A descrição é o prompt — testado com números reais, nesta sessão

A primeira versão de rolar_teste em tools.py tinha a descrição mais curta possível: "atributo": {"type": "string", "description": "atributo"}. Rodando scripts/tool_call_accuracy.py — 10 cenários fixos, cada um com o estado da cena e a ação esperada — contra a Groq de verdade, o resultado foi 70% de acerto completo (ferramenta certa + argumentos certos). Um dos erros: pedido para escalar um muro, o modelo chamou rolar_teste(atributo="atletismo", cd=15) — "atletismo" não é um atributo de D&D 5e, é uma perícia. A ferramenta certa, o argumento errado, porque nada no schema dizia quais valores eram válidos.

A correção não foi no código Python — foi só reescrever o JSON Schema, adicionando um "enum":

"atributo": {
    "type": "string",
    "enum": ["forca", "destreza", "constituicao", "inteligencia", "sabedoria", "carisma"],
    "description": "O atributo mais relevante para a ação (força para escalar/arrombar, ...)."
}

Rodando o mesmo script de novo, sem mudar nenhuma linha de Python: 80%. O caso do "atletismo" sumiu — o modelo passou a escolher sempre entre os seis atributos válidos. Isso é o achado central da lição: a descrição e o schema de uma ferramenta não são documentação para humanos, são a única informação que o modelo tem para decidir certo. Um enum vazio de exemplo, uma frase genérica onde devia ter um exemplo concreto — isso é, literalmente, a diferença entre 70% e 80% medida na mesma tarde, no mesmo modelo, na mesma cadeia de cenários.

Achado 1Prompt engineering para tool calling não é escrever um parágrafo bonito na description da função — é o enum, o exemplo dentro da própria descrição do parâmetro ("ex: '1d6', '2d6+2'"), o "NUNCA use esta ferramenta para X, use Y" explícito. É engenharia de restrição, não de prosa. E dá para medir o efeito de uma mudança específica com um número antes/depois — não precisa ficar no "parece que melhorou".

Ter a ferramenta não é o mesmo que usá-la

O achado mais desconfortável desta etapa não veio do script — veio de testar ao vivo contra o servidor rodando de verdade. Mandei "Eu me esforço para perceber o perigo escondido nas sombras" — uma ação óbvia para rolar_teste(atributo="sabedoria", cd=...). A resposta:

"...role um teste de Percepção (CD 12) lançando um d20 para determinar se Kaelen detecta o perigo."

Nenhuma chamada de ferramenta. O modelo narrou pedindo o dado ao jogador — o mesmo comportamento que o ADR-0006 já tinha documentado na Etapa 3, quando o mecanismo era JSON solto. Adicionei uma instrução explícita no prompt de sistema ("chame rolar_teste você mesmo, na hora — NUNCA peça ao jogador para rolar") e testei de novo, em uma sessão nova. Mesmo resultado. Um terceiro teste, pedindo para arrombar um baú: de novo, "role um d20 e me informe o resultado".

Por que isso importa mais do que pareceÉ tentador pensar que dar ao modelo a ferramenta certa resolve o problema — afinal, na Etapa 3 o argumento era "o modelo não pode calcular dano de forma confiável, então tire isso dele". Mas ter rolar_teste disponível não muda o hábito de treino do modelo de simular ser um mestre de RPG de mesa, onde é o jogador humano que joga o dado físico. tool_choice="auto" deixa a decisão de chamar ou não a cargo do modelo — e para testes de perícia informais, ele prefere narrar a pedir. Corrigir isso de verdade provavelmente exige tool_choice forçado em contextos específicos, não mais uma frase de instrução — ficou registrado como aberto no ADR-0007.
Achado 2Tool calling resolve o problema de schema (o modelo não pode mais inventar um JSON com forma errada) mas não resolve, sozinho, o problema de hábito (o modelo pode simplesmente optar por não chamar a ferramenta e narrar em texto livre, como sempre fez). São dois problemas diferentes que parecem o mesmo até você medir os dois separadamente — o primeiro se resolve com schema; o segundo, aparentemente, não.
