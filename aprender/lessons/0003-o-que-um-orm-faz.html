Lição 03 · Mestre.IA

O que um ORM faz, de verdade

A Lição 1 já avisou: se você editar combat_state no lugar em vez de atribuir um objeto novo, a mudança some no commit() — sem erro, sem aviso. Esta lição explica por que isso acontece, usando o mecanismo real do SQLAlchemy (não "é assim que funciona, decore"), e por que ele sobrevive à Etapa 2 mesmo depois do api.py virar quatro camadas.

~12 minutos Arquivos: app/infra/db.py · app/routers/game.py Lição 1 — o caminho de uma jogada ↗

Em app/infra/db.py, Personagem é uma classe Python comum, só que herda de Base (SQLAlchemy). Isso não é decoração — é o que faz heroi.hp_atual deixar de ser um atributo Python qualquer e virar o que o SQLAlchemy chama de atributo instrumentado. Por baixo, cada coluna mapeada (Mapped[int], Mapped[str]...) vira uma propriedade especial que, quando você atribui um valor a ela (heroi.hp_atual = 7), dispara um evento: "este atributo, deste objeto, mudou". É esse evento que o SQLAlchemy usa para saber o que escrever no próximo commit() — sem ele, o ORM não teria como saber que algo mudou sem comparar o objeto inteiro contra o banco toda vez.

A sessão lembra o que você tocou, não o que você fez

Cada requisição do Mestre.IA ganha uma Session nova (get_db(), app/infra/db.py — é o que o Depends(get_db) de cada router injeta). Uma Session mantém, na memória, um "mapa de identidade": para cada linha do banco que ela já carregou nesta requisição, existe exatamente um objeto Python representando ela. Quando você faz heroi.hp_atual = 7, a Session não escreve no banco na hora — ela só marca o objeto heroi como "sujo" (dirty). Só no commit() ela percorre tudo que está sujo e gera o UPDATE de verdade. Esse padrão tem nome: Unit of Work — acumular mudanças e aplicar todas de uma vez, em vez de uma escrita por atribuição.

É exatamente aqui que mora a armadilha. O evento "este atributo mudou" dispara quando você atribui (heroi.combat_state = algo). Ele não dispara quando você muta o valor por dentro — porque, do ponto de vista do Python, heroi.combat_state["ativo"] = True nunca toca no atributo combat_state do objeto heroi. Ele pega o dicionário que já estava lá (uma referência) e muda uma chave dele. O SQLAlchemy nunca é chamado — não há evento, não há "sujo", não há UPDATE.

Por que isso não acontece com uma coluna IntegerSe hp_atual fosse mutável e você fizesse algo como heroi.hp_atual += 1, isso também é, por baixo, uma atribuição (heroi.hp_atual = heroi.hp_atual + 1) — o operador += em Python sempre reatribui para tipos imutáveis como int. O problema é exclusivo de colunas JSON guardando algo mutável (dict, list), porque só esses tipos permitem mudar o conteúdo sem reatribuir a variável que aponta para eles.

O código já sabia disso — veja onde

app/routers/game.py, no fim de chat_endpoint, é a prova ao vivo:

novo_hist = list(heroi.historico_chat)
novo_hist.append({"role": "user", "content": user_input.action})
novo_hist.append({"role": "assistant", "content": narrativa})
heroi.historico_chat = novo_hist          # reatribuição — dispara o evento
heroi.combat_state = c_state.model_dump() # idem
db.commit()

list(heroi.historico_chat) cria uma lista nova (uma cópia rasa) em vez de reaproveitar a que já estava no objeto. O código então mexe só nessa cópia — nunca na lista original que o SQLAlchemy está de olho. No fim, heroi.historico_chat = novo_hist troca o atributo pela lista nova inteira. É essa troca, não os dois .append(), que o SQLAlchemy enxerga. Se o código tivesse feito heroi.historico_chat.append(...) direto, os dois append teriam efeito na memória — a lista Python mudaria — mas o commit() gravaria o banco exatamente como estava antes. Um bug silencioso: nenhuma exceção, nenhum log, só uma mensagem de chat que "sumiu" depois do F5.

A regra de bolsoColuna JSON guardando dict/list: sempre trate como imutável do lado de fora. Leia, copie (ou, como o Mestre.IA faz desde a Etapa 2, valide para um modelo Pydantic com model_validate), mude a cópia, e devolva com uma atribuição nova no final. Nunca mexa direto no que heroi.combat_state devolve.

Por que a Etapa 2 não resolveu isso — e não devia

Existe uma correção de verdade para essa classe de bug: o SQLAlchemy tem uma extensão, sqlalchemy.ext.mutable, que embrulha o dict/list num tipo que intercepta mutação e dispara o evento sozinho — MutableDict.as_mutable(JSON) na definição da coluna, e combat_state["ativo"] = True passaria a funcionar sem reatribuição. O Mestre.IA não adotou isso na Etapa 2, de propósito: domain/state.py já resolve o problema por outro caminho — os campos JSON viram modelos Pydantic (CombatState, WorldState, QuestLog) assim que saem do banco, o código de negócio nunca mais toca no dict cru, e a gravação final sempre passa por .model_dump() seguido de atribuição — que já dispara o evento corretamente. Ensinar "sempre reatribua" para quem vai mexer no motor de regras da Etapa 3 é mais barato, e mais transferível para qualquer outro ORM, do que instalar uma extensão que resolve só este sintoma.

Duas coisas que você já sabe agora

Achado 1O SQLAlchemy não observa o seu objeto em Python — ele observa atribuições a atributos mapeados. Mutação em memória (um .append(), um dict[chave] = valor) é invisível para o ORM, porque nenhuma dessas operações passa pela propriedade instrumentada que dispara o evento de "sujo". É a mesma razão pela qual, em Python puro, lista_a = lista_b não copia a lista — só copia a referência.
Achado 2O bug de coluna JSON silenciosa e o bug de "validar só no front" (Lição 2) têm a mesma forma: os dois são casos de confiar em algo que atravessou uma fronteira sem confirmar do outro lado — lá, a fronteira era rede (navegador → servidor); aqui, é a fronteira entre "objeto Python na sua mão" e "o que a Session está observando". Fronteiras que não avisam quando são cruzadas errado são o padrão mais comum de bug silencioso neste projeto.
