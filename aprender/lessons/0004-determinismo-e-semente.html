Determinismo, semente, e como testar dado sem trapacear

A Etapa 3 escreveu 63 testes para um motor de combate que rola d20 de verdade — e nenhum deles depende de sorte. test_natural_20_sempre_acerta_e_e_critico força um 20 sem rodar a função 200 vezes esperando que ele apareça. Esta lição explica o mecanismo por trás disso: por que random.Random é uma classe, e não só um punhado de funções soltas, e como esse detalhe vira a diferença entre "testei e pareceu funcionar" e "testei e sei que funciona".

~10 minutos Arquivos: app/services/rules_engine.py · app/services/combat.py · tests/test_rules_engine.py Lição 3 — o que um ORM faz ↗

O problema: como você testa uma função que rola dados?

resolver_ataque(bonus_ataque, ca_alvo) precisa acertar às vezes e errar às vezes — é literalmente o que a função existe para decidir. Mas se ela chama random.randint(1, 20) direto, todo teste vira uma aposta: assert resultado.acerto só passa quando o dado colabora. A saída ingênua — rodar a função 200 vezes e conferir que o resultado tende a ficar certo — é exatamente o que test_rules_engine.py já fazia para rolar_dado() desde a Etapa 1 (for _ in range(200): assert 1 <= rolar_dado("1d20") <= 20). Isso prova que a função não quebra, mas nunca prova um caso específico: "quando o d20 sai 20, é sempre crítico, mesmo com um bônus de -10". Testar isso com sorte exigiria rodar a suíte até um 20 aparecer — e torcer.

Injeção de dependência disfarçada de parâmetro opcional

A saída real é simples de enunciar e fácil de esquecer de aplicar: a função não deveria decidir de onde vem a aleatoriedade — quem chama ela é que decide. Em produção, "de onde vem" é o gerador global do Python. Em teste, é qualquer coisa que você controle. Toda função estocástica do motor segue o mesmo formato:

def resolver_ataque(bonus_ataque: int, ca_alvo: int, rng: random.Random | None = None) -> ResultadoAtaque:
    dado = rng or random
    rolagem = dado.randint(1, 20)
    ...

Isso é injeção de dependência com o mínimo de cerimônia possível — sem container, sem framework, só um parâmetro com valor padrão. Em produção, ninguém passa rng; dado vira o módulo random global, e o jogo joga de verdade. Em teste, você passa um gerador com sequência conhecida, e a função — sem saber, sem precisar saber — usa exatamente os números que você escolheu.

random.Random é uma classe, não só um módulo

É fácil nunca perceber isso: import random; random.randint(1, 20) parece uma função solta, como len(). Por baixo, o módulo random mantém uma instância global de random.Random e delega toda chamada a ela — random.randint é, na prática, _instância_global.randint. Como é uma classe de verdade, dá para instanciar a sua própria: random.Random(42) cria um gerador com semente fixa, que sempre produz a mesma sequência de números para a mesma semente. É esse objeto — não o módulo — que os testes passam como rng.

Semente (seed) não é o mesmo que sequência controladaUma semente fixa (random.Random(42)) garante reprodutibilidade — rodar duas vezes dá o mesmo resultado — mas você ainda precisaria descobrir, por tentativa, qual semente produz um 20 na terceira chamada. O Mestre.IA vai um passo além: tests/test_rules_engine.py define RngFixo, uma subclasse de random.Random que ignora a semente e devolve, em ordem, exatamente os valores que o teste passou:

class RngFixo(random.Random):
    def __init__(self, valores: list[int]) -> None:
        super().__init__()
        self._valores = iter(valores)

    def randint(self, a: int, b: int) -> int:
        return next(self._valores)

resolver_ataque(bonus_ataque=-10, ca_alvo=15, rng=RngFixo([20])) não deixa dúvida: o próximo randint() vai devolver 20, sempre, não importa quantas vezes você rode o teste. É assim que test_natural_20_sempre_acerta_e_e_critico prova a regra "natural 20 sempre acerta, mesmo com bônus terrível" sem depender de sorte nenhuma.

O bug de tipo que essa mesma sessão encontrou

Vale registrar um tropeço real, porque ensina mais que um exemplo limpo. Em services/combat.py, o primeiro rascunho de iniciar_combate fazia dado = rng or random uma vez, no topo da função, e reaproveitava dado em toda chamada — inclusive nas que delegam para rules_engine.py. O mypy recusou:

error: Argument 2 to "rolar_iniciativa" has incompatible type "Random | Module"; expected "Random | None"
Por que isso é um erro de tipo real, não só chatice do mypyrng or random tem tipo random.Random | ModuleType — o módulo random não é uma instância de random.Random, mesmo se comportando como uma (ele expõe os mesmos métodos, por delegação). Toda função do motor espera random.Random | None e resolve o or random por dentro de si mesma. Passar adiante o resultado de um or já resolvido é passar o tipo errado — a correção foi parar de pré-resolver e simplesmente repassar o `rng` original (o `Optional`) para cada chamada, deixando cada função decidir seu próprio fallback.

A lição segura: quando um padrão precisa se repetir em vários lugares (aqui, "use o rng se ele existir, senão o global"), resolva ele uma vez, no nível mais baixo — dentro de cada função que efetivamente rola o dado — não no nível de quem orquestra. Isso também é o que já fazia `rules_engine.py` sozinho; o bug só apareceu quando `combat.py` tentou "ser esperto" e resolver o fallback cedo demais.

Por que isso importa mais do que "os testes passam"

O critério de pronto da Etapa 3, no PLANO_MESTRE.md, é literal: "você roda a suíte 100 vezes e ela dá o mesmo resultado 100 vezes". Sem injeção de aleatoriedade, isso seria uma contradição — testar um sistema aleatório de forma determinística soa como um paradoxo até você perceber que o sistema não precisa ser determinístico, só precisa ser determinístico quando alguém pedir para ser. É o mesmo truque usado para testar relógios (freeze_time), UUIDs (uuid4 mockado) ou qualquer chamada de rede (a Etapa 6 vai usar respx para o mesmo fim, mockando a Groq em vez do random). O padrão se repete: identifique a fonte de não-determinismo, isole-a atrás de um parâmetro, e injete uma versão controlável só em teste.

Achado 1"Testável" não é uma propriedade que código aleatório ganha por acidente — é uma escolha de design. A diferença entre random.randint() chamado direto e rng.randint() com rng injetável é uma linha, mas ela é o que separa "só dá para testar as bordas do intervalo" de "dá para testar qualquer cenário específico, exato, sob demanda".
Achado 2Um bug de tipo do mypy (Random | Module onde se esperava Random | None) não é burocracia — ele pegou, em tempo de checagem, uma decisão de design errada (resolver o fallback cedo demais) que só apareceria em produção se alguém, por acidente, tentasse chamar um método que só existe em random.Random e não no módulo random (ou vice-versa). O tipo forçou a pergunta certa antes do código rodar.
