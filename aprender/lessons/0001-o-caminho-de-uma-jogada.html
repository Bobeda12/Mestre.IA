O caminho de uma jogada

Você digita “ataco o goblin” e aperta Enter. Seis peças de software entram em ação, em ordem. Esta lição segue essa jogada do começo ao fim — e dá nome a cada peça.

~12 minutos Arquivos: GameChat.tsx · api.py · database.py Glossário do stack ↗

Antes de mudar qualquer coisa no Mestre.IA, você precisa conseguir contar essa história de cabeça. Não porque é bonito — mas porque toda pergunta de entrevista sobre o seu projeto é alguma variação de “o que acontece quando o usuário faz X?”. Quem sabe traçar o caminho consegue responder qualquer uma delas.

A jogada tem seis paradas. Em cada uma, uma biblioteca diferente é dona do problema.

As seis paradas

1

O clique

Dono: React — Frontend/src/components/GameChat.tsx

React não é um framework de aplicação, é uma biblioteca de interface. A ideia central dele é: você não manda a tela mudar, você muda um estado e o React recalcula a tela sozinho.

const [messages, setMessages] = useState<Message[]>([]);
// ...
setMessages(prev => [...prev, { role: 'user', content: text }]);

Você nunca escreveu “adicione um balão de texto na tela”. Você só acrescentou um item numa lista. O React comparou a lista nova com a antiga e desenhou a diferença. Esse é o modelo mental inteiro (react.dev, “State: A Component's Memory”).

2

A viagem

Dono: axios — GameChat.tsx, função sendAction

const res = await axios.post("http://127.0.0.1:8000/chat",
                             { session_id: currentSessionId, action: text });

Aqui o navegador e o Python deixam de compartilhar memória. Tudo que atravessa essa linha vira texto. O axios pega o seu objeto JavaScript, serializa em JSON, põe o cabeçalho Content-Type: application/json e dispara um POST (docs do axios).

Por que isso importaEssa fronteira é a razão de existir o session_id. O backend não tem ideia de quem você é entre uma requisição e outra — HTTP não guarda memória. O session_id é a etiqueta que permite reencontrar o seu herói no banco.
3

A porta

Dono: FastAPI + Pydantic, servidos por Uvicorn — Backend/api.py

class UserAction(BaseModel):
    session_id: str; action: str

@app.post("/chat")
async def chat_endpoint(user_input: UserAction, db: Session = Depends(get_db)):

Três bibliotecas dividem esse trabalho, e confundi-las é o erro mais comum:

  • Uvicorn é o servidor. É ele que fica escutando na porta 8000 e fala HTTP.
  • FastAPI é o roteador. Olha o caminho /chat e decide qual função sua chamar.
  • Pydantic é o porteiro. Aquela classe UserAction não é decoração: se chegar um corpo sem action, ou com action sendo um número, o Pydantic devolve 422 e a sua função nunca roda (FastAPI, “Request Body”).

O Depends(get_db) é o sistema de injeção de dependência do FastAPI: antes de chamar a sua função, ele executa get_db(), abre uma sessão de banco, entrega para você — e, quando a resposta termina, roda o finally: db.close(). Você nunca esquece de fechar a conexão porque não é você quem fecha.

4

A memória

Dono: SQLAlchemy sobre SQLite — Backend/database.py

heroi = db.query(HeroModel).filter(HeroModel.session_id == user_input.session_id).first()

SQLAlchemy é um ORM: ele traduz classes Python em tabelas SQL e de volta. Essa linha vira, por baixo, um SELECT * FROM herois WHERE session_id = ? LIMIT 1 — e o resultado volta como um objeto Python com atributos.

SQLite é o banco em si: um arquivo único, rpg_save.db, sem servidor separado. Ótimo para desenvolver, e é a peça que vai ter que mudar quando você for para a nuvem.

Detalhe que confunde muita genteAs colunas world_state, combat_state e historico_chat são do tipo JSON. O SQLAlchemy só percebe que elas mudaram se você atribuir um objeto novo. É exatamente por isso que o código faz c_state = dict(heroi.combat_state), mexe na cópia, e depois heroi.combat_state = c_state. Se você editasse o dicionário no lugar, a alteração se perderia silenciosamente no commit.
5

O cérebro

Dono: groq (SDK) + o modelo llama-3.3-70b-versatile — api.py

prompt = montar_contexto(heroi, w_state, c_state, q_state)   # a bíblia + o estado
hist   = list(heroi.historico_chat)[-4:]                   # só as 4 últimas!
msgs   = [{"role": "system", "content": prompt}] + hist + [{"role": "user", ...}]

resp = client.chat.completions.create(model=MODEL_NAME, messages=msgs,
                                      response_format={"type": "json_object"})

Três coisas acontecem aqui, e vale separá-las:

  1. O contexto é remontado do zero a cada turno. O modelo não “lembra” de nada entre chamadas — é uma função sem memória. Toda a memória do jogo vem do banco e é reinjetada como texto.
  2. A biblia_mestre.txt vira a mensagem system. Ela é lida uma vez quando o servidor sobe (a classe DataManager, em data_manager.py, carrega tudo no __init__) e colada em todo turno.
  3. O response_format força saída em JSON. É um recurso do provedor, não uma promessa do prompt — o Groq garante sintaxe JSON válida nesse modo (Groq, “Structured Outputs”). Note que ele garante sintaxe, não os campos que você pediu.
Guarde este número[-4:]. Quatro mensagens. É por isso que o mestre esquece o que você fez dez turnos atrás — não é limitação do modelo, é uma linha do seu código.
6

A volta

Dono: SQLAlchemy grava, FastAPI serializa, React redesenha

heroi.historico_chat = novo_hist
heroi.combat_state = c_state
db.commit()
return { "narrativa": narrativa, "hp_atual": heroi.hp_atual, ... }

O db.commit() é o ponto em que a jogada vira permanente. Depois disso, o FastAPI transforma o dicionário em JSON, o axios recebe, e o React chama vários setState — o que dispara um novo desenho da tela. Fim da volta.

Duas coisas que você já sabe agora

Achado 1A amnésia do mestre tem endereço: api.py, o fatiamento [-4:]. Não é “o modelo é ruim”. É uma decisão de código que você pode mudar.
Achado 2O prompt em montar_contexto pede "hp_atual" ao modelo — mas olhe o return: o código devolve heroi.hp_atual, o valor que já estava no banco. O valor que o modelo escreve é jogado fora. Ou seja: hoje o HP nunca muda. Nem o modelo nem o motor governam o dano — ninguém governa.

Esse segundo achado é a semente da fase mais importante do seu roadmap. O consenso hoje é justamente esse: um LLM serve para decidir qual ferramenta chamar e narrar o resultado, não para ser a fonte da verdade do estado (Anthropic, “Building effective agents”).
