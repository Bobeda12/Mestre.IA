O contrato entre front e back

O front pode mandar qualquer coisa. Literalmente — não é força de expressão. Esta lição usa o bug real que a Etapa 1 consertou (o servidor ignorava os atributos que você escolhia no wizard) para explicar por que "validar no front" nunca é suficiente, e o que o Pydantic faz de verdade quando barra uma requisição.

~12 minutos Arquivos: api.py · CharacterCreation.tsx Lição 1 — o caminho de uma jogada ↗

Antes da Etapa 1, o passo 4 do wizard de criação (CharacterCreation.tsx) fazia você gastar 27 pontos de point-buy entre seis atributos, com barra, contador e tudo. Parecia uma regra de verdade. Mas olhe o que o handleFinish mandava para o servidor:

const res = await axios.post("http://127.0.0.1:8000/create_character", {
  nome: name, raca: selectedRace, classe: selectedClass,
  alinhamento: alignment, background: background, objetivo: goal,
  historia_texto: history
  // os atributos que você acabou de gastar 27 pontos escolhendo? não vão.
});

E do outro lado, Backend/api.py nem tinha onde recebê-los: a função simplesmente escrevia 15/14/13/12/10/10 fixo para todo personagem. O wizard inteiro era teatro — uma interface bonita conectada a um servidor que não escutava.

Por que "validar no front" nunca resolve sozinho

A tentação óbvia seria: "então bota uma checagem no React antes de mandar". Mas pense em onde esse código roda. O JavaScript da sua aplicação executa no navegador do usuário — numa máquina que você não controla. Nada impede alguém de abrir o DevTools, ou usar curl direto, e mandar isto:

curl -X POST http://127.0.0.1:8000/create_character \
  -H "Content-Type: application/json" \
  -d '{"nome":"Trapaceiro","raca":"Humano","classe":"Guerreiro",
       "atributos":{"forca":99,"destreza":99,"constituicao":99,
                     "inteligencia":99,"sabedoria":99,"carisma":99},
       "atributos_livre":[], "alinhamento":"Neutro",
       "background":"x","objetivo":"x"}'

Esse curl nunca passa pelo React. Não existe wizard, não existe barra de pontos, não existe nenhum código JavaScript no caminho. Se a única validação estivesse no front, essa requisição chegaria intacta. Validação de front é experiência do usuário — evita que ele erre sem querer. Validação de back é segurança — impede que alguém erre de propósito. São dois problemas diferentes, e um não substitui o outro.

A regra de bolsoNunca confie em nada que atravessou a fronteira entre navegador e servidor sem checar de novo do lado de cá. A fronteira em si (ver Lição 1, parada 2) é o ponto onde qualquer garantia do front deixa de valer.

O que o Pydantic faz, de fato

É aqui que entra o "porteiro" que a Lição 1 já tinha nomeado. Depois da Etapa 1, CharacterCreationRequest em api.py ganhou um validador de verdade:

class CharacterCreationRequest(BaseModel):
    atributos: dict[str, int]
    atributos_livre: list[str] = []

    @field_validator("atributos")
    @classmethod
    def valida_point_buy(cls, valores: dict[str, int]) -> dict[str, int]:
        if set(valores.keys()) != ATRIBUTOS_VALIDOS:
            raise ValueError(...)
        custo_total = sum(CUSTO_PONTOS[v] for v in valores.values())
        if custo_total > PONTOS_DISPONIVEIS:
            raise ValueError(...)
        return valores

Um field_validator é uma função que o Pydantic roda depois de confirmar o tipo do campo (aqui, "isso é um dicionário de string para inteiro") e antes de deixar o valor entrar no objeto final. Se a função levantar ValueError, a requisição inteira é recusada — sua função create_character nunca chega a rodar. É por isso que o curl do exemplo acima, hoje, recebe 422 Unprocessable Entity em vez de criar um personagem com 99 de força (docs do Pydantic, "Validators").

O que o Pydantic não consegue sozinhoO field_validator de atributos_livre confere formato (nomes válidos, sem repetição) — mas não confere se a raça escolhida realmente dá aquele ponto livre. Essa checagem (api.py:186, dentro de create_character) precisa saber quantos pontos livres a raça concede, e essa informação vive em data_manager.regras, um arquivo JSON — não em nada que o Pydantic enxergue a partir do corpo da requisição sozinho. Por isso a validação da Etapa 1 ficou em duas camadas: uma no modelo (formato), outra na função (regra que depende de outro dado). O ADR-0002 registra essa divisão e por quê.

E o lado do front, agora?

O React continua calculando o point-buy para dar feedback imediato (a barra de pontos restantes, o botão "Próximo" que só libera com 0 pontos sobrando) — isso não vai embora, porque é o que torna o wizard usável. A diferença é que agora ninguém confia nesse cálculo: ele é só uma sugestão amigável. O servidor refaz a conta do zero.

O ROADMAP_PORTFOLIO.md e o PLANO_MESTRE.md citam Zod como a peça que fecha esse contrato pelo lado do front — validando as respostas que chegam do backend antes de confiar nelas, o par simétrico do Pydantic. Vale registrar com honestidade: até esta etapa, o front ainda não usa Zod — ele chama axios puro e confia na forma da resposta. Isso é trabalho da Etapa 7 (PLANO_MESTRE.md §6). O motivo de mencionar aqui é o conceito, não a biblioteca: o mesmo problema (não confiar em dado que atravessou a fronteira) existe nos dois sentidos, e hoje só um lado está coberto.

Duas coisas que você já sabe agora

Achado 1Antes da Etapa 1, o wizard de criação inteiro — as barras, os botões +/-, o contador de pontos — não tinha nenhum efeito no personagem criado. Era uma interface completa conectada a um servidor que descartava tudo. O bug não estava em nenhuma lógica quebrada; estava num campo que simplesmente nunca foi adicionado ao corpo da requisição.
Achado 2"Validar no front" e "validar no back" não são a mesma tarefa feita em dois lugares — são duas tarefas diferentes. Uma existe para guiar quem usa a interface; a outra existe para resistir a quem não usa. Um projeto com API pública (e toda API HTTP é, tecnicamente, pública) precisa das duas, mas só pode confiar numa delas.
