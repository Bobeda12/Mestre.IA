Streaming do servidor ao pixel — o caminho de um token

Até a Etapa 6, POST /chat é uma chamada clássica de pergunta-resposta: o cliente manda a ação, o servidor roda o loop de ferramentas inteiro e só devolve JSON quando a narrativa completa já está pronta. O jogador olha pra tela parada até o texto inteiro aparecer de um golpe. Esta lição segue um token desde o modelo até o pixel — e no meio do caminho encontra um problema que a maioria dos tutoriais de streaming não menciona: o que fazer com a cadeia de fallback (Etapa 4) quando você já mandou texto pro cliente e o modelo cai no meio da frase?

~12 minutos Arquivos: app/infra/llm_client.py · app/services/agent_loop.py · app/routers/game.py · Frontend/src/lib/sse.ts Lição 7 — como se testa um sistema que não é determinístico ↗

Por que "streaming" não é só um efeito de máquina de escrever

Dá para simular um efeito de digitação inteiramente no cliente: pega a resposta completa (que já chegou, do jeito de sempre) e revela um caractere por vez com setInterval. Isso parece streaming, mas não muda uma coisa que importa de verdade: o tempo até o jogador ver qualquer coisa continua sendo o tempo da resposta inteira. Streaming de verdade — o servidor mandando cada pedaço assim que o modelo o produz — reduz esse tempo até o primeiro pedaço visível, porque o cliente não precisa mais esperar o último token pra ver o primeiro.

Essa é a métrica que importa aqui: tempo até o primeiro token, não o tempo total. É por isso que a Etapa 7 pediu pra medir, não só implementar — sem número, "parece mais rápido" é opinião.

SSE, não WebSocket, não polling

Três jeitos de um servidor entregar dado incremental pro navegador: polling (cliente pergunta "terminou?" de novo e de novo — não resolve o problema, o texto só aparece quando o polling flagra o turno pronto), WebSocket (canal bidirecional completo, mas o servidor deste jogo nunca precisa iniciar uma mensagem por conta própria — é sempre pergunta→resposta) e Server-Sent Events (SSE — um único fluxo HTTP, unidirecional servidor→cliente, exatamente a forma deste problema). ADR-0012 tem a tabela completa de alternativas; aqui fica só o resumo: SSE é o formato mais simples que resolve exatamente o que precisa ser resolvido, nem mais nem menos.

O problema que ninguém avisa: fallback e streaming não combinam de graça

A Etapa 4 deu ao jogo uma cadeia de modelos (ADR-0008): se o modelo principal falhar, tenta o próximo da lista. Isso é seguro numa chamada de resposta única — nada foi mostrado ao jogador ainda, então trocar de modelo por baixo dos panos é invisível. Mas com streaming, depois do primeiro chunk, o jogador já viu texto sendo narrado por um modelo específico. Se a conexão cair no meio e o código trocar silenciosamente pro próximo modelo, o resto da frase sai com outro "narrador" — dois estilos costurados numa resposta só, sem o jogador nunca saber que isso aconteceu.

# app/infra/llm_client.py — chamar_stream_com_fallback (resumido)
for modelo in MODELOS:
    try:
        stream = _chamar_modelo(modelo, msgs, tools, tool_choice, stream=True)
    except (_ERROS_TRANSITORIOS, groq.APIStatusError):
        continue  # ainda não mandou nada pro cliente — pode trocar de modelo

    comprometido = False
    try:
        for chunk in stream:
            comprometido = True
            yield chunk
        return
    except _ERROS_TRANSITORIOS as e:
        if comprometido:
            raise ErroMestre("A conexão com a IA caiu no meio da resposta.") from e
        continue  # falhou antes do 1º chunk — ainda pode trocar
A regra em uma fraseFallback só é seguro antes do primeiro chunk. Depois disso, a stream está "comprometida" com aquele modelo — uma falha vira erro explícito pro jogador, nunca uma troca silenciosa.

De chunk a evento: o que executar_turno_stream faz

agent_loop.executar_turno (Etapa 4) já sabia rodar o loop de ferramentas até a narrativa final. executar_turno_stream faz a mesma coisa, mas devolve um generator de eventos em vez de um resultado só, no fim: token (um pedaço de texto de narração), tool_event (uma ferramenta acabou de resolver — carrega o dado estruturado da rolagem, da Fase 1 desta etapa) e erro.

Um detalhe que só apareceu testando contra a Groq de verdade, não em nenhum teste com LLM falso: o modelo usado neste projeto (openai/gpt-oss-120b) manda tokens de raciocínio — o "pensamento" interno antes de decidir o que narrar — num campo separado do chunk (delta.reasoning, channel: "analysis"), diferente do campo de conteúdo público (delta.content). Como o código só olha delta.content pra decidir o que virar evento token, esse raciocínio nunca vaza pra tela — mas ele ainda consome tempo antes do primeiro token visível, o que importa pra próxima seção.

Deltas de ferramenta nunca viram "token"Enquanto o modelo está montando os argumentos de uma chamada de ferramenta (JSON chegando aos poucos), isso também vem em chunks — mas não interessa ao jogador ver um {"a aparecendo na tela. executar_turno_stream acumula esses pedaços em silêncio e só produz um evento quando a ferramenta já foi executada de verdade, com o resultado.

Sem EventSource: por que um parser SSE feito à mão

A API nativa do browser pra consumir SSE, EventSource, só sabe fazer GET — e este turno precisa mandar session_id/action no corpo de um POST. A solução é fetch normal (que aceita POST) lendo o corpo como um ReadableStream, com um parser pequeno (Frontend/src/lib/sse.ts) cortando esse fluxo de bytes em frames event: ...\ndata: ...\n\n:

// lib/sse.ts (resumido) — o buffer é o que garante que um frame
// cortado entre dois pacotes de rede não se perde
let buffer = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buffer += decoder.decode(value, { stream: true });
  let sepIndex;
  while ((sepIndex = buffer.indexOf("\n\n")) !== -1) {
    yield parseFrame(buffer.slice(0, sepIndex));
    buffer = buffer.slice(sepIndex + 2);
  }
}

O detalhe que um parser ingênuo erraria: a rede não entrega um frame SSE inteiro de uma vez só — o separador "\n\n" pode cair bem no meio, entre dois pacotes TCP diferentes. Sem o buffer acumulando entre leituras, metade de um frame chegaria num chunk e a outra metade no próximo, e um parser que só olha um chunk por vez perderia o frame inteiro. Frontend/src/lib/sse.test.ts tem um teste dedicado a exatamente esse caso.

Medindo de verdade: o achado desconfortável

Rodando um turno real contra a Groq (não um LLM falso) — o herói agindo sem combate, um passo de ferramenta (mover) seguido de narração — o primeiro token visível saiu em ~1,26 segundos, com o texto inteiro terminando pouco depois disso. Isso não é rede lenta: é o tempo que o modelo gasta no canal de raciocínio (seção anterior) antes de emitir qualquer conteúdo público. Streaming ainda ajuda — o resto do texto aparece token a token, em vez de tudo de uma vez no fim — mas não elimina essa espera inicial.

A lição real aqui"Streaming reduz o tempo até o primeiro token" é verdade — mas pra um modelo de raciocínio, esse "primeiro token" ainda carrega o custo do pensamento escondido. A otimização de percepção que o streaming promete depende de quanto do tempo total é raciocínio vs. geração de texto público — não é grátis nem uniforme entre modelos.
