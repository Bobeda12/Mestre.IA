Lição 10 · Mestre.IA

Do localhost à internet — o que muda quando não é mais a sua máquina

Até a Etapa 8, front e back sempre foram o mesmo site — localhost, portas diferentes. A Lição 09 já tinha achado um bug ali (localhost × 127.0.0.1 contam como sites diferentes para SameSite), mas o conserto foi simples: alinhar os dois no mesmo hostname. Em produção essa saída não existe — *.vercel.app e *.fly.dev nunca vão ser o mesmo domínio. Esta lição é sobre o que isso muda de verdade, e sobre uma coleção de bugs que só apareceram testando contra a internet de verdade, não em nenhum teste automatizado.

~12 minutos Arquivos: Frontend/vercel.json · Backend/app/infra/settings.py · Backend/app/infra/llm_client.py Lição 9 — sessão, cookie e token ↗

O problema que o deploy criou (e localhost nunca teve)

O cookie de sessão do Mestre.IA (Lição 09) é httpOnly, SameSite=Lax, sem Secure. Em localhost, alinhar front e API no mesmo hostname bastava para o navegador tratar as duas origens como mesmo site — portas diferentes não importam para SameSite. Em produção, front (mestre-ia-seven.vercel.app) e API (mestre-ia-backend.fly.dev) são domínios registráveis diferentes de verdade. Não existe hostname comum para alinhar — a saída da Lição 09 não se aplica mais.

SameSite=Lax não é enviado numa requisição cross-site que não é navegação de topo — e todo fetch/axios do front cai nessa categoria. O sintoma seria idêntico ao da Lição 09: POST /auth/login volta 200 com o cookie visível na resposta, e o próximo pedido autenticado volta 401, como se o cookie nunca tivesse existido.

Duas saídas — e por que este projeto escolheu a menos óbvia

A correção "óbvia" seria trocar samesite="lax" por samesite="none" e adicionar secure=True nas três chamadas de set_cookie em routers/auth.py. Isso resolveria o 401 — mas abriria uma porta nova: navegadores com tracking prevention agressivo (Safari ITP, e o Chrome vem endurecendo isso) podem bloquear cookies de terceiro mesmo com SameSite=None; Secure corretamente configurado, porque do ponto de vista deles um cookie setado por um domínio diferente do que está na barra de endereço é exatamente o padrão que rastreamento entre sites usa.

Este projeto escolheu a outra saída: fazer a Vercel agir como proxy de /api/* para o Fly.io.

// Frontend/vercel.json
{
  "rewrites": [
    { "source": "/api/(.*)", "destination": "https://mestre-ia-backend.fly.dev/$1" },
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Com isso, o navegador só enxerga https://mestre-ia-seven.vercel.app/api/... — nunca o domínio do Fly.io diretamente. Front e API viram a mesma origem do ponto de vista do navegador, o cookie volta a ser first-party, e SameSite=Lax continua funcionando sem tocar em routers/auth.py nenhuma linha. A segunda regra do vercel.json (reescrever qualquer outra rota para index.html) resolve um problema separado: sem ela, navegar direto para /entrar (em vez de clicar num link dentro do app) dava 404 — a Vercel não sabia que essa rota pertence ao React Router, uma single-page app só tem um HTML de verdade.

Por que isso não é só "trocar o sintoma pela causa"O proxy elimina a categoria de bug inteira, não só o 401 específico. SameSite=None; Secure resolveria o teste manual de hoje e deixaria uma dependência de comportamento de navegador que pode mudar (tracking prevention vem ficando mais agressivo com o tempo, não menos). Proxy não depende de nenhuma política de terceiro continuar do jeito que está.

CORS e cookie cross-site são dois problemas diferentes

É fácil confundir os dois porque os sintomas se parecem — um pedido "não funciona" entre dois domínios. Mas resolvem coisas diferentes: CORS é o navegador perguntando ao servidor "esta origem tem permissão para ler a resposta desta chamada?" (allow_origins em app/main.py). SameSite é o navegador decidindo, por conta própria, se envia o cookie numa chamada cross-site — o servidor não participa dessa decisão. Configurar CORS certinho e ainda assim tomar 401 por causa de SameSite é o sintoma clássico de confundir os dois. Com o proxy, CORS deixa de ser um problema também: front e API são a mesma origem, então nem existe mais uma chamada cross-origin para o navegador negociar.

Uma coleção de bugs que só existem fora do localhost

Nenhum dos bugs abaixo apareceu em pytest, ruff, ou mypy — os 215+ testes do backend continuaram verdes o tempo inteiro. Todos só apareceram testando contra os serviços reais.

1. JSON num secret de linha de comando

cors_origins era um list[str] — pydantic-settings exige JSON estrito (["a","b"]) para preencher esse tipo a partir de uma variável de ambiente. Passar isso pelo PowerShell (fly secrets set 'CORS_ORIGINS=["https://..."]') chegou corrompido no servidor: o backend crashava na inicialização com SettingsError ao tentar decodificar o JSON mastigado pelo shell. A correção não foi só escapar melhor as aspas — foi trocar o tipo do campo para uma string simples separada por vírgula, parseada por uma @property (cors_origins_list). Um formato mais simples de passar por linha de comando é uma robustez de produção, não só um jeito de evitar um bug específico.

# app/infra/settings.py
cors_origins: str = "http://localhost:5173"

@property
def cors_origins_list(self) -> list[str]:
    return [o.strip() for o in self.cors_origins.split(",") if o.strip()]

2. O Git Bash "corrigindo" um caminho que não era caminho nenhum

Configurar VITE_API_URL=/api na Vercel pelo Git Bash (MSYS) no Windows produziu, sem nenhum erro visível, o valor C:/Program Files/Git/api — o MSYS reescreve automaticamente argumentos de linha de comando que parecem um caminho absoluto do Unix (começam com /) para o caminho Windows equivalente, mesmo quando o argumento não é um caminho de arquivo, é só uma string que por acaso começa com barra. A correção: MSYS_NO_PATHCONV=1 antes do comando, para desligar essa conversão só para aquela chamada.

Por que isso é traiçoeiroNão deu erro nenhum — o comando "funcionou", só que salvou o valor errado silenciosamente. Só apareceu porque o build seguinte ainda continha a string localhost:8000 (o valor de fallback do código) em vez de /api — um `curl`/inspeção do bundle gerado é o que revelou o valor real salvo.

3. Um parâmetro que o SDK simplesmente não tem

Pedir stream_options={"include_usage": True} na chamada da Groq (para capturar tokens no streaming, para o Langfuse) parecia inofensivo — é um parâmetro padrão em APIs compatíveis com OpenAI. O SDK da Groq instalado (groq==0.37) não aceita esse parâmetro, e a chamada falhava com TypeError — quebrando todo turno em streaming, o caminho principal que o jogo usa desde a Etapa 7. Um teste local ao vivo contra a API de verdade (não contra um double/mock) pegou isso antes do deploy; a correção foi remover o parâmetro e aceitar que o streaming não reporta tokens ao Langfuse (o resto da trace — modelo, texto, latência — continua valendo).

4. A chave certa, a região errada

O Langfuse Cloud tem regiões separadas (EU e US) com hosts diferentes — e chaves de uma região não autenticam na outra. Usar o host padrão (EU, cloud.langfuse.com) com uma chave de uma conta US devolveu 401 Unauthorized silencioso no exportador de traces, sem derrubar o app (o SDK do Langfuse falha "por fora", sem quebrar a chamada real ao modelo — desenhado assim de propósito, tracing não deveria nunca poder derrubar o produto). Langfuse.auth_check() contra os dois hosts foi o que revelou qual região a conta realmente usava.

O padrão por trás dos quatro

Nenhum desses bugs é sobre lógica de negócio errada — são todos sobre a borda entre o código e o ambiente que o executa: um shell reescrevendo um argumento, um SDK sem um parâmetro que a documentação de outro serviço sugeria existir, uma região de conta que não é a assumida por padrão. Esse tipo de bug é estruturalmente invisível a pytest — testes automatizados rodam contra doubles e mocks, exatamente para não depender do estado de rede/ambiente de quem roda. É o mesmo princípio que a Etapa 4 já tinha achado para chamadas de LLM, e a Etapa 8 para o cookie de sessão: **testar contra o serviço real, cedo, antes de considerar a etapa pronta** — não só ao final, e não só com curl/httpx quando o que importa é o comportamento de um navegador de verdade (a Lição 09 já tinha essa mesma ressalva).
