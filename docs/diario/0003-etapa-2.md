# Etapa 2 — Arquitetura auditável

**Período:** 19/08/2026 · **Tempo gasto:** ~3h numa sessão só, com o Claude Code fazendo boa parte da digitação mecânica (a estimativa do plano, ~25h, supõe uma pessoa sozinha escrevendo tudo à mão — vale registrar essa diferença em vez de comparar os dois números como se fossem a mesma coisa)

## O que eu queria com essa etapa

`Backend/api.py` tinha 291 linhas fazendo tudo: rotas, chamada à IA, validação de regras, acesso a banco. As Etapas 3 e 4 do plano vão triplicar esse código (motor de regras, chamadas de ferramenta). Esta etapa troca a fundação por baixo — sem mudar nada que o jogador veja — antes que o código cresça demais para reorganizar com segurança.

## O que mudou

- **`api.py` virou um pacote (`Backend/app/`)** com quatro pastas, cada uma respondendo a uma pergunta diferente: `routers/` (só HTTP), `services/` (a lógica — falar com a IA, calcular regras, cortar o histórico recente), `domain/` (a forma dos dados, com Pydantic), `infra/` (banco, configuração, o client da IA, os arquivos de regras). Nenhum arquivo passa de ~150 linhas.
- **A configuração deixou de ser `os.getenv()` espalhado** e virou uma classe só (`Settings`, biblioteca `pydantic-settings`) que lê o `.env` e valida os tipos. Isso resolveu de graça um problema que os testes já tinham documentado: o caminho do banco era relativo à pasta onde você mandava rodar o comando, não ao arquivo — hoje é sempre um caminho absoluto.
- **O banco ganhou uma tabela de usuário.** Antes, o "personagem" e a "sessão" eram a mesma coisa (a mesma coluna era chave primária). Agora existe `usuario` (hoje só um, fixo, criado sozinho quando o servidor sobe) e `personagem` aponta para ele. Isso não muda nada para quem joga hoje — é preparação para a tela de login da Etapa 8, feita agora porque trocar a chave primária de uma tabela *depois* que ela tiver dado de gente de verdade é a operação mais cara que existe, e hoje ainda não tem.
- **O banco passou a ser gerenciado por Alembic** (uma ferramenta de "migrations" — controla, de forma ordenada, como o formato do banco muda ao longo do tempo). Antes, cada mudança de coluna exigia apagar o banco de teste e deixar o código recriar do zero (foi o que a Etapa 1 fez). Agora existe um histórico de mudanças que dá para aplicar (ou desfazer) sem apagar nada.
- **Ganhou lint e checagem de tipos** (`ruff` e `mypy`), rodando tanto localmente quanto num robô do GitHub a cada mudança enviada (`CI`, de "integração contínua" — roda os testes automaticamente antes de aceitar qualquer mudança). Se algum teste falhar, ou a cobertura de teste cair abaixo de 60% no código de regras, a mudança fica marcada como "não passou", visível no README.
- **Ganhou Docker** — um jeito de empacotar o projeto inteiro (backend e frontend) para subir com um comando só, sem precisar instalar Python e Node na máquina de quem só quer rodar.
- **O README virou a porta de entrada de engenharia** que já tinha sido prometida desde a Etapa 0: diagrama da arquitetura, como rodar dos dois jeitos (direto ou via Docker), e uma lista honesta do que o jogo ainda não faz.

## O que quebrou no caminho

**Um servidor antigo, esquecido rodando de uma sessão anterior, travou o arquivo do banco.** Ao tentar apagar o `rpg_save.db` velho (preciso, porque o formato da tabela mudou — `usuario`/`personagem` no lugar de `herois`), o Windows recusou: "arquivo em uso". Um processo `uvicorn` de um teste manual anterior ainda estava de pé, com o arquivo aberto. Precisei encerrar esse processo antes de conseguir apagar o banco velho e deixar o Alembic criar o novo.

**O Docker Desktop não estava ligado.** O comando `docker` existe nesta máquina, mas o "motor" dele (o programa Docker Desktop, que fica rodando em segundo plano) não estava de pé — os comandos de build falhavam com um erro de conexão. Precisei abrir o Docker Desktop manualmente e esperar ele terminar de subir antes de conseguir testar qualquer coisa.

**`uv run` baixava as ferramentas de desenvolvimento dentro do container, toda vez que ele iniciava.** O `Dockerfile` instala as dependências com `uv sync --frozen --no-dev` (sem `ruff`, `mypy`, `pytest` — ferramentas que só fazem sentido em desenvolvimento). Mas o comando que sobe o servidor usava `uv run alembic ...` e `uv run uvicorn ...` sem o mesmo `--no-dev` — e `uv run` sempre confere se o ambiente está sincronizado com o `pyproject.toml` antes de rodar qualquer coisa, então ele reinstalava as ferramentas de dev (~26 MB) toda vez que o container ligava, mesmo elas nunca sendo usadas. Só apareceu porque *olhei o log* do container depois de subir — o comando `docker compose up` não teria avisado sozinho. Corrigido adicionando `--no-dev` também nos dois `uv run` do `CMD`.

## Decisões tomadas

- [ADR-0003](../adr/0003-camadas-router-service-domain-infra.md) — por que separar em `router`/`service`/`domain`/`infra`, e não outra divisão.
- [ADR-0004](../adr/0004-alembic-para-migrations.md) — por que adotar uma ferramenta de migrations agora, e não continuar apagando o banco a cada mudança.
- [ADR-0005](../adr/0005-usuario-personagem-antes-do-login.md) — por que a tabela de usuário nasce três etapas antes de existir uma tela de login.

## Números

- 33 testes automatizados passando (eram 28 no fim da Etapa 1; os 5 novos testam a validação de atributos como função isolada, sem precisar subir o servidor inteiro para isso).
- Cobertura de teste em `app/domain` e `app/services`: 77% — acima da meta de 60% que o plano pedia para esta etapa.
- `ruff` (lint) e `mypy` (checagem de tipos) rodando limpos, sem nenhum aviso.
- Testei o fluxo inteiro contra o servidor rodando de verdade, com a chave da Groq configurada: criar personagem → recarregar a ficha → mandar uma ação de chat → resposta da IA processada e salva. Mesmo formato de resposta de antes da etapa — nada quebrou para quem joga.
- `docker compose up --build` sobe os dois serviços: o backend aplica a migration sozinho e responde em `localhost:8000`, o front (build de produção) responde em `localhost:5173`.

## O que eu faria diferente

Conferir se havia algum servidor antigo rodando *antes* de começar a apagar arquivos, não depois de tomar o erro. É o tipo de coisa que uma pessoa trabalhando sozinha esqueceria também — mas um `just backend-dev` sempre em primeiro plano (em vez de rodar em segundo plano e esquecer) evitaria esse acúmulo silencioso.

## O que ficou para depois

- A tabela `usuario` só tem uma linha fixa até a Etapa 8. Não é bug, é o plano — mas vale lembrar da próxima vez que aparecer no schema e parecer "usuário morto".
- `rolar_dado()` continua devolvendo `0` em silêncio para entrada inválida — comportamento caracterizado de propósito em teste (`tests/test_rules_engine.py`), aguardando a correção de verdade na Etapa 3.
