# Etapa 1 — Consertar as mentiras

**Período:** 19/08/2026 · **Tempo gasto:** ~2h30 (o plano previa 12h, mas ainda falta o teste manual de longo prazo — ver "o que ficou para depois")

## O que eu queria com essa etapa

A Etapa 0 deixou o projeto rodável. Esta etapa ataca os bugs mais graves do diagnóstico do `PLANO_MESTRE.md`: coisas que a interface promete e o jogo não cumpre. Recarregar a página perdia o personagem. Os 27 pontos de atributo que você escolhia no wizard eram jogados fora — o servidor sempre criava o mesmo personagem, não importa o que você escolhesse. A Defesa do personagem só existia no navegador, não no banco. E quando a IA falhava por qualquer motivo, você via só `"..."` na tela, sem saber por quê.

## Uma bifurcação antes de começar

Antes de tocar em código, encontrei um problema: o diretório de trabalho tinha mudanças que ninguém tinha commitado ainda — nem as da Etapa 0 (que já estava pronta, só esquecida sem commit), nem um experimento anterior em `api.py`, `database.py` e nos componentes do front (um prólogo gerado por IA, um "diário de missão" guardado no banco). Esse experimento não corrigia nenhum dos bugs do diagnóstico — era um caminho paralelo.

Perguntei o que fazer, e a decisão foi: commitar os dois separadamente (Etapa 0 primeiro, depois o experimento como um "retrato" isolado, deixando claro no texto do commit que ele é anterior ao plano), para não perder nenhum trabalho, e só então começar a Etapa 1 de verdade em cima dessa base. Isso significa que a Etapa 1 corrige bugs num código um pouco diferente do que o diagnóstico original descrevia linha por linha — mas os bugs em si (atributos ignorados, Defesa solta, `except` genérico, sessão perdida no F5) continuavam todos lá.

## O que mudou

- **A sessão foi para a URL.** Antes, `/jogar` dependia de um valor guardado só na memória do React (`App.tsx`) — que some toda vez que a página recarrega. Agora a rota é `/jogar/:sessionId` (o `:sessionId` é um "parâmetro de rota": o React Router lê esse pedaço da URL e entrega para o componente). O `GameChat` busca o estado do personagem direto do servidor usando esse id, então dar F5 não perde mais nada. O `localStorage` (um armário de dados que o navegador guarda entre visitas) continua existindo, mas só como lista de atalhos para a tela inicial — não é mais o dono da verdade.
- **O servidor passou a receber e revalidar os atributos.** O wizard já calculava os 27 pontos de "point-buy" (o sistema de D&D onde cada valor de atributo tem um custo em pontos, e você tem um orçamento fixo para gastar) — mas nunca mandava isso para o backend. Agora manda, e o servidor confere de novo: será que os valores estão na faixa certa (8 a 15)? será que o total gasto não passa de 27? será que o "ponto livre" da raça (algumas raças, como Meio-Elfo, dão um bônus extra que você escolhe onde colocar) foi usado num atributo válido? Se qualquer checagem falhar, o servidor recusa com uma mensagem explicando o motivo — ele não confia mais no que o navegador manda, porque nada impede alguém de pular o navegador inteiro e chamar a API direto (com uma ferramenta como `curl`, por exemplo).
- **A Defesa (CA) virou uma coluna no banco.** Antes só existia no `localStorage`; hoje o servidor calcula a partir da Destreza já validada e guarda junto com o resto da ficha.
- **A história que você escreve no wizard agora entra no prólogo.** O campo já existia e o front já mandava — só ninguém do outro lado lia. Agora o texto que o jogador escreve entra no prompt (o texto de instrução que vai para a IA) que gera a introdução da aventura.
- **Os erros da IA ganharam mensagem própria.** Antes, qualquer problema — chave de API ausente, tempo esgotado, cota estourada, resposta em formato errado — caía num `except:` genérico (um "pegue qualquer erro, não importa qual" do Python) que sempre mostrava `"..."` para o jogador. Agora cada causa tem uma função que sabe identificá-la e devolve uma frase explicando o que aconteceu.

## O que quebrou no caminho

**O banco de dados de teste precisou ser apagado.** Como o projeto ainda não tem um sistema de migrations (Alembic, ferramenta que altera o formato de um banco já existente sem perder os dados — chega só na Etapa 2), adicionar a coluna nova de Defesa significava que o arquivo `rpg_save.db` antigo, criado com o formato velho, não ia ganhar a coluna sozinho. Como é só um save de teste (a Etapa 0 já tinha documentado isso), apaguei o arquivo e deixei o próprio código recriar o banco do zero, já no formato novo.

**O build do front reclamou de importações que não eram minhas.** Ao rodar `tsc` (o verificador de tipos do TypeScript, que também aponta código nunca usado) pela primeira vez desde que peguei o projeto, ele acusou cinco ícones importados e nunca usados nos componentes — sobra do experimento commitado antes da Etapa 1. Limpei, porque um build que não passa não serve para confirmar nada.

**A ferramenta de "achar elemento por descrição" do navegador não funcionou.** Eu queria clicar em botões pelo nome ("botão Meio-Elfo", "botão PRÓXIMO") em vez de decorar a posição deles na árvore da página, mas a busca por texto não achou nada, nenhuma vez. Não travou o trabalho — só troquei para ler a árvore de acessibilidade inteira a cada passo e clicar pela referência exata (tipo `ref_16`) — mas foi mais lento do que devia.

- 5 dos 9 bugs do diagnóstico original consertados nesta etapa (os outros seguem no plano: combate, memória do mestre, inventário — todos dependem do motor de regras da Etapa 3)

## O que eu faria diferente

Rodar `tsc` (o verificador de tipos) logo de cara, antes de escrever qualquer linha nova, para separar o que já estava quebrado do que eu estava introduzindo. Fiz isso só depois de terminar as mudanças do front, o que funcionou, mas verificar antes teria evitado a dúvida de "isso é meu ou já estava assim?" no meio do caminho.

## O que ficou para depois

- O critério de "pronto" da Etapa 1 pede também testar em duas abas/navegadores diferentes — fiz só o teste de recarregar a mesma aba. Vale repetir com o Chrome de verdade em algum momento, não só no navegador de teste.
- HP durante o jogo continua sem dono: a IA ainda pode "dizer" que você tomou dano e isso não é gravado em lugar nenhum. Esse bug (o #3 do diagnóstico original) é da Etapa 3 (o Juiz), não desta.
- O `.claude/launch.json` que criei para testar o front no navegador de dentro do Claude Code ficou no repositório, mas fora do commit desta etapa — é conveniência de desenvolvimento, não faz parte do produto.
