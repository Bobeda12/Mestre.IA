# Etapa 0 — Rodar e provar

**Período:** 19/08/2026 · **Tempo gasto:** ~1h30 (o plano previa 8h)

## O que eu queria com essa etapa

Antes de hoje, para colocar o projeto para rodar era preciso instalar um monte de biblioteca que nem era usada mais (um resto do Google que sobrou de antes de eu trocar para a Groq), e o arquivo que lista essas bibliotecas (`requirements.txt`) estava salvo num formato de texto que só funciona no Windows — abre errado em qualquer outro sistema. Também não existia teste automático de verdade: só um script (`teste.py`) que eu precisava rodar na mão, com o servidor já ligado em outro terminal, e que nem avisava se algo desse errado — ele não tinha nenhum `assert` (a linha que faz um teste realmente *falhar*, com um alarme vermelho, quando o resultado não é o esperado; sem ela, o script só imprime números na tela e você tem que olhar e decidir sozinho se está certo).

A ideia da Etapa 0 é simples: alguém — inclusive eu, daqui a três meses, já tendo esquecido os detalhes — consegue baixar o projeto do zero e colocá-lo para rodar em poucos minutos, com uma forma de checar sozinho que nada quebrou.

## O que mudou

- **Troquei a forma de instalar as bibliotecas do backend.** Antes era `pip` (o instalador padrão do Python) mais uma pasta `venv` — um "ambiente virtual", isto é, uma pasta isolada onde ficam as bibliotecas só deste projeto, sem misturar com o resto do computador. Agora uso uma ferramenta chamada `uv`, que faz a mesma coisa, só que mais rápida, e com uma vantagem que importa mais: ela grava um arquivo (`uv.lock`) com o número exato de cada versão instalada. Sem esse arquivo, se eu instalar hoje e você instalar amanhã, cada um pode acabar com uma versão ligeiramente diferente de alguma biblioteca — e aí o projeto funciona na minha máquina e quebra na sua, sem nenhuma mudança de código, só por causa disso.
- **Tirei do projeto 14 bibliotecas do Google** (do SDK do Gemini, o modelo de IA do Google) que ficaram esquecidas de uma fase anterior à troca para a Groq. Antes de remover, conferi linha por linha que nenhum arquivo do projeto de fato usava (`import`) alguma delas.
- **Corrigi uma linha antiga em `database.py`.** Ela buscava uma peça (`declarative_base`) de um endereço dentro da biblioteca SQLAlchemy (a que conversa com o banco de dados) que já está avisando "isso vai parar de existir". Troquei para o endereço atual — uma linha só, mas evita que o projeto simplesmente pare de funcionar numa atualização futura do SQLAlchemy.
- **Parei de guardar o arquivo de save (`rpg_save.db`) dentro do git.** Ele já devia estar fora — existia até uma regra pedindo isso (no `.gitignore`, a lista de arquivos que o git deve ignorar) — mas o arquivo tinha sido salvo no projeto antes dessa regra existir, e a regra sozinha não desfaz isso, só evita repetir daqui para frente. Rodei um comando que tira o arquivo do controle de versão sem apagá-lo do seu computador — ele continua aí, só não vai mais junto quando eu enviar mudanças para o GitHub.
- **Troquei o `teste.py` por testes de verdade**, numa pasta nova `Backend/tests/`. São 21 verificações automáticas que rodam em cerca de 1 segundo, sem precisar ligar o servidor manualmente. Elas usam uma peça do próprio FastAPI que simula um servidor "de mentirinha" rodando dentro do mesmo programa — então dá para testar as rotas da API sem realmente abrir uma porta de rede.
- **Criei um arquivo de atalhos** (`justfile`): em vez de decorar o comando inteiro para subir o backend ou rodar os testes, agora dá para digitar `just backend-dev` ou `just backend-test`. Isso precisa de uma ferramentinha chamada `just`, que instalei no Windows.
- **Escrevi um README simples**, só com o passo a passo de como rodar o projeto do zero.

## O que deu errado no caminho — a parte que mais vale registrar

**Errei o nome do pacote na hora de instalar o `just`.** Pedi para o Windows instalar `Casey.Just.Just`, chutando um padrão de nome que outros programas usam (repetido duas vezes), e ele respondeu que não achou nada com esse nome. A solução foi simples: perguntar direto para o instalador (`winget search just`) e ver o nome certo, que era só `Casey.Just`, sem repetição. Bobo, mas vale anotar — da próxima vez que eu for instalar algo assim, procuro o nome primeiro em vez de chutar.

**Um aviso confuso da ferramenta de testes.** Eu tinha dito explicitamente para o pytest (quem roda os testes) onde procurar os arquivos de teste, e mesmo assim ele reclamava "não encontrei nada aí" — mesmo com os arquivos exatamente naquele lugar. Na prática não travava nada: ele encontrava os testes de outro jeito, por garantia, e rodava tudo certinho — só a mensagem de aviso ficava sobrando. Não fui atrás da causa exata; é provavelmente algum detalhe de como esse computador lida com o "endereço" de uma pasta (estou rodando por dentro do Git Bash, um terminal que finge ser Linux só dentro do Windows, e essas duas coisas às vezes discordam sobre como escrever um caminho de pasta). Tirei aquela instrução explícita, e o aviso sumiu — o jeito automático já encontra os arquivos certos sozinho. Prefiro escrever aqui "não sei exatamente por quê, mas resolvi assim e funcionou" do que fingir que entendi tudo.

**O `just`, recém-instalado, não aparecia de cara.** Isso é uma chatice comum do Windows: quando você instala um programa novo, o sistema atualiza uma lista interna de "onde procurar programas quando alguém digitar um comando" — só que os terminais que já estavam abertos não sabem que essa lista mudou. Só os terminais novos, abertos depois da instalação, enxergam o programa novo. Não é um problema do projeto, é só preciso lembrar: depois de instalar algo assim, abra um terminal novo.

## O que eu decidi, e por quê

O porquê completo da troca para `uv` está num documento separado, feito para durar — [ADR-0001](../adr/0001-uv-para-dependencias.md). Resumindo: era a opção mais rápida entre as que eu considerei, e resolvia o problema pela raiz (nenhuma trava de versão) em vez de só consertar o sintoma (o arquivo que abria errado).

## Números, para não ficar só na sensação de "acho que melhorou"

- 21 testes, nenhum falhando, rodando em cerca de 1,3 segundo
- Apaguei a pasta inteira onde as bibliotecas ficam instaladas e reinstalei tudo do zero, só para simular "computador de outra pessoa" — funcionou, em 4,4 segundos, sem eu precisar mexer em nada
- 32 bibliotecas instaladas agora, contra 44 de antes (as 14 do Google saíram; o resto da diferença é dependência que uma biblioteca puxava para outra sozinha)

## O que eu faria diferente

Antes de tentar instalar alguma coisa nova pelo nome, procurar o nome certo primeiro. Parece óbvio escrito assim — na hora eu fui direto no chute.
