# Etapa 4 — O narrador

**Período:** 19/08/2026 · **Horas reais:** uma sessão só com o Claude Code escrevendo a maior parte do código (não cronometrei o tempo de parede desta vez — diferente das etapas anteriores, prefiro registrar isso do que inventar um número) · **estimado no plano:** ~25h / 3 semanas

## O que eu queria com essa etapa

Desde a Etapa 3, o mestre (o LLM, o modelo de linguagem que narra o jogo) continuava dizendo o que o jogador queria fazer escrevendo um pedacinho de JSON solto no meio da narrativa — `comando_combate: {"tipo": "atacar", "arma": "...", "alvo": "..."}`. O servidor confiava nesse campo só porque o nome batia, sem checar a forma dele de verdade. Essa etapa troca isso pelo mecanismo de verdade das APIs de LLM modernas: **tool calling** (chamada de ferramenta) — o modelo, em vez de escrever texto que *parece* estruturado, chama uma função de verdade (`atacar(alvo="Goblin", arma="Cimitarra")`), com os argumentos já validados pela própria API antes de chegarem no meu código.

## O que mudou

- **Nove ferramentas que o modelo pode chamar**, em vez de um campo de JSON solto: `rolar_teste` (testar um atributo, tipo força ou destreza, contra uma dificuldade), `atacar`, `aplicar_dano` (dano que não vem de arma — queda, armadilha), `mover`, `consultar_regra`, `usar_item`, `dar_item`, `gastar_ouro` e `iniciar_combate`. As oito primeiras já estavam no plano; a nona (`iniciar_combate`) eu adicionei porque deixar um campo solto (`spawn_battle`) sobrevivendo ao lado de ferramentas de verdade ia contra o próprio objetivo da etapa.
- **Um loop de agente com limite de passos.** Uma chamada de ferramenta não vem com narrativa junto — o modelo primeiro chama, só depois de ver o resultado (`"ACERTO! 6 de dano"`) é que escreve a prosa. Isso significa ida e volta com a API pelo menos duas vezes por turno de combate. O limite (6 passos) existe para o jogo nunca ficar preso pagando cota da Groq (o provedor de LLM que uso, tem um plano gratuito com limite de uso) num loop sem fim.
- **Uma cadeia de modelos de reserva (fallback).** Se o modelo principal (`openai/gpt-oss-120b`) estourar a cota gratuita ou falhar, o sistema tenta automaticamente um segundo modelo (`openai/gpt-oss-20b`), depois um terceiro (`qwen/qwen3.6-27b`), com duas tentativas em cada um antes de desistir e cair pro próximo (usando a biblioteca `tenacity`, que sabe esperar um pouco entre tentativas). Antes desta etapa, um erro de qualquer tipo derrubava o turno inteiro sem alternativa.
- **Um "fiscal" de narrativa (guardrail).** Depois que o modelo termina de narrar, um checador simples confere se o texto contradiz o que o servidor sabe ser verdade — um item citado como se estivesse na mochila mas não está, um inimigo já morto tratado como se ainda estivesse atacando, um local diferente do atual. Se achar contradição, pede ao modelo uma correção (uma segunda chamada, sem ferramenta, só texto). Não é perfeito — é busca por palavra-chave, não entendimento de verdade — e documentei os limites dele abaixo.
- **Uma coluna de ouro de verdade.** O personagem não tinha dinheiro nenhum guardado no banco até agora — `gastar_ouro` precisava de algo para debitar, então criei a coluna (com uma migration do Alembic, a ferramenta que versiona mudanças de estrutura do banco) com 10 de ouro inicial.
- **Uma métrica de verdade: tool-call accuracy** — em cenários fixos, quantas vezes o modelo chama a ferramenta certa com os argumentos certos. Medi antes e depois de reescrever as descrições das ferramentas: **70% → 80%**.

## O que quebrou no caminho

**O modelo pede ao jogador para rolar o dado, mesmo tendo a ferramenta disponível.** Testando ao vivo (servidor rodando de verdade, personagem real, ação real digitada), mandei "eu me esforço para perceber o perigo escondido nas sombras" — uma ação óbvia para a ferramenta `rolar_teste`. A resposta foi só narrativa pedindo "role um teste de Percepção (CD 12)". Adicionei uma instrução explícita no texto de sistema ("chame a ferramenta você mesmo, nunca peça ao jogador para rolar") e testei de novo, numa sessão nova — mesmo resultado. Um terceiro teste, tentando arrombar um baú, de novo a mesma coisa. É o mesmo comportamento que a Etapa 3 já tinha documentado (o modelo pedindo dado ao jogador mesmo sem ter essa opção), só que sobrevivendo à troca de mecanismo — ter a ferramenta certa não é o mesmo que o modelo escolher usá-la. Fica registrado como limitação conhecida, não persegui até resolver de vez (ver "o que ficou para depois").

**O modelo narrou um item sendo guardado no inventário sem chamar a ferramenta que guarda de verdade.** Numa cena de saque, a resposta dizia "Kaelen guarda os itens no seu inventário" — mas o inventário real, no banco, não mudou nada. Corrigi o texto de sistema pedindo para chamar `dar_item` *antes* de narrar a posse, mas não teve tempo de confirmar se isso resolve de verdade ou só reduz a frequência (o mesmo padrão do problema acima).

**O `mover` teve o mesmo problema, e o meu "fiscal" (guardrail) não pegou.** Pedi para viajar até a Vila de Phandalin; a narrativa descreveu a viagem inteira, chegada incluída — mas `mover` nunca foi chamado, e o local salvo no banco continuou o antigo. O guardrail deveria pegar isso (é exatamente pra esse tipo de caso que ele existe), mas ele procura o nome exato do local repetido no texto, e a narrativa só citava "Vila de Phandalin" uma vez, no começo, como destino pretendido — depois só dizia "a vila". Uma checagem por palavra-chave tem esse limite: ela só pega o que se repete do jeito que ela espera.

**`rolar_teste` não existia — precisei escrever o motor primeiro.** A Etapa 3 previa "testes de atributo contra CD" como parte do motor de regras, mas isso nunca chegou a ser escrito (só ataque e teste de morte tinham resolução própria). Precisei adicionar `resolver_teste_atributo` no motor antes de poder expor a ferramenta.

## Decisões tomadas

- [ADR-0007](../adr/0007-tool-calling-em-vez-de-json-solto.md) — por que tool calling nativo em vez de continuar validando JSON solto, e os três casos ao vivo de "narrou sem chamar a ferramenta".
- [ADR-0008](../adr/0008-cadeia-de-fallback-de-modelo.md) — a cadeia de modelos de reserva, e por que ela é entre modelos da Groq (não um segundo provedor de verdade) por decisão de escopo, não de código.
- [Lição 05](../../aprender/lessons/0005-anatomia-de-uma-chamada-com-ferramentas.html) — o que realmente viaja na rede quando se manda `tools=[...]`, e o salto de 70% para 80% de acerto só de reescrever a descrição de uma ferramenta.

## Números

- 107 testes automatizados passando (eram 63 no fim da Etapa 3) — 44 novos, cobrindo as ferramentas (`tools.py`, 95% de cobertura), o loop de agente (`agent_loop.py`, 100%), o guardrail (`guardrail.py`, 100%) e a cadeia de fallback (`llm_client.py`).
- Cobertura total de `app/`: 89% — acima da meta de 60%.
- `ruff` e `mypy` limpos.
- Tool-call accuracy: 70% → 80% (10 cenários, medidos duas vezes com o mesmo script contra a API de verdade).
- Testado ao vivo: criei um personagem de verdade, um Goblin real apareceu do bestiário, ataquei e vi a rolagem real na tela (`d20(12)+5=17 vs CA 15 → ACERTO! 4 de dano`), o combate acabou em vitória — e três limitações genuínas apareceram testando ações fora do roteiro óbvio (teste de percepção, saque, viagem), documentadas acima em vez de escondidas.

## O que eu faria diferente

Teria testado ao vivo *antes* de escrever os testes automatizados, não depois. Os testes automatizados (com resultado de dado controlado, previsível) provam que cada ferramenta funciona isoladamente — e provaram, sem nenhum problema. Mas os três bugs reais desta etapa (pedir rolagem ao jogador, narrar item sem guardar, narrar viagem sem mover) só apareceram testando com o modelo de verdade, escrevendo ação livre como um jogador escreveria. Testes automatizados provam que o motor está certo; só uma sessão ao vivo prova que o modelo está *usando* o motor.

## O que ficou para depois

- Os três casos de "o modelo narra uma mudança de estado sem chamar a ferramenta" continuam acontecendo às vezes, mesmo depois do ajuste de prompt. Resolver de vez provavelmente exige forçar `tool_choice` (obrigar o modelo a considerar uma ferramenta, em vez de deixar "automático") em contextos específicos — não testei isso ainda.
- O guardrail é busca por palavra-chave, não entendimento de frase. Ele vai continuar perdendo casos onde a narrativa parafraseia em vez de repetir o nome exato — um LLM-as-judge (um segundo modelo, menor e mais barato, checando a resposta do primeiro) resolveria melhor, mas isso é escopo da Etapa 6.
- `usar_item` só tem efeito mecânico definido para um item (Poção de Cura). Qualquer outro item "funciona" narrativamente sem mudar número nenhum — não existe um sistema de itens completo, e não é escopo desta etapa criar um.
- A cadeia de fallback entre modelos foi testada com um cliente falso (sem rede), não com uma cota de verdade estourada — forçar isso ao vivo exigiria gastar a cota gratuita de propósito, o que não fiz.
